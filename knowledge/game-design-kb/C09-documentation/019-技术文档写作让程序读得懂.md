# 技术文档写作：让程序读得懂

## 核心观点
策划写给程序的文档和写给制作人的文档完全不同。技术需求文档追求的是"无二义性"和"可实现性"，而不是"有吸引力"。好的技术文档应该让程序无需开会就能直接开工。

## 方法论

### 技术文档必备模块
1. **功能概述**：一句话说清楚这个功能是什么
2. **前置依赖**：需要哪些系统/模块已经就绪
3. **数据结构**：核心数据模型（表结构/字段定义）
4. **接口定义**：前后端交互的请求/响应格式
5. **状态机**：核心对象的状态转换图
6. **流程时序**：关键操作的时序图
7. **异常处理**：每种异常的处理策略
8. **性能约束**：QPS/响应时间/内存限制

### 无二义性写作法则
- ❌ "玩家可以获得一些奖励" → ✅ "玩家获得 gold×100 + exp×50"
- ❌ "在合适的时机触发" → ✅ "当玩家连续登录7天时，在第8天登录时触发"
- ❌ "性能要好" → ✅ "单帧计算耗时 < 2ms，内存增量 < 10MB"
- ❌ "参考XX游戏" → ✅ "参考XX游戏的Y功能，具体差异点：Z"

### 接口文档模板
```
接口名称: 领取每日奖励
请求方式: POST
路径: /api/daily_reward/claim
请求参数:
  - player_id: string (必填, 玩家ID)
  - day_index: int (必填, 第几天, 1-30)
返回参数:
  - code: int (0=成功, 1001=已领取, 1002=未到时间)
  - reward_list: array<RewardItem> (奖励列表)
异常处理:
  - 网络超时: 客户端重试3次，间隔2s
  - 重复请求: 服务端幂等，返回已领取状态
```

### 策划vs程序思维差异
| 策划思维 | 程序思维 |
|----------|----------|
| "这里弹个窗" | "弹窗的触发条件/内容/按钮/关闭逻辑？" |
| "做个排行榜" | "实时还是定时刷新？TOP多少？并列怎么处理？" |
| "随机掉落" | "哪种随机算法？保底机制？种子怎么处理？" |

## 检查清单
- [ ] 所有数值是否精确到具体数字
- [ ] 每个接口是否定义了异常处理
- [ ] 状态转换是否画了状态机图
- [ ] 边界情况是否全部列出
- [ ] 程序是否无需额外沟通就能开发

## 核心框架

### 埋点设计三原则

1. **为假设而埋**: 每个埋点回答一个设计假设（"我认为玩家会在这里卡住"→埋点验证）
2. **宁多勿少但有规范**: 上线后补埋点成本极高，但无规范的埋点是数据灾难
3. **事件+属性+时间戳**: 每条埋点必须包含"谁+在哪+做了什么+什么结果+什么时间"

### 埋点分类矩阵

| 类型 | 内容 | 典型事件 |
|------|------|---------|
| **生命周期** | 注册/登录/升级/付费/流失 | user_register / level_up / first_pay |
| **核心循环** | 关卡开始/结束/胜负/耗时 | battle_start / battle_end / battle_result |
| **系统交互** | 打开界面/点击按钮/功能使用 | ui_open / button_click / feature_use |
| **经济行为** | 获取资源/消耗资源/交易 | resource_gain / resource_spend |
| **社交行为** | 加好友/组队/聊天/公会 | friend_add / team_join |
| **异常检测** | 崩溃/卡顿/异常操作 | crash / performance_drop |

### 埋点文档标准格式

```
事件名: battle_end
触发条件: 战斗结算完成
属性:
  - battle_id: string (战斗唯一ID)
  - result: enum (win/lose/draw)
  - duration_sec: int (战斗时长秒)
  - player_level: int
  - enemy_type: string
  - damage_dealt: int
  - damage_taken: int
  - skill_used: array (使用技能列表)
```

## 设计检查清单

- [ ] 每个核心系统是否都有"开始/结束/结果"三段埋点？
- [ ] 关键漏斗的每一步是否都有事件追踪？
- [ ] 埋点文档是否规范（事件名/触发条件/属性列表）？
- [ ] 上线前是否做过埋点验证（数据是否正确回传）？

# 敏捷开发在游戏项目中的实践

## 核心观点
游戏开发天生适合敏捷——需求不确定、创意迭代频繁、需要快速验证手感。但纯Scrum在游戏项目中也有水土不服的地方，需要因地制宜地改造。

## 方法论

### Scrum在游戏中的适配
| Scrum概念 | 游戏项目适配 |
|-----------|-------------|
| Sprint | 2-4周一个迭代，对齐版本节奏 |
| Product Owner | 制作人/主策划 |
| Scrum Master | 项目经理/PM |
| Sprint Planning | 版本规划会（确定本迭代目标功能） |
| Daily Standup | 每日站会（15分钟，昨天/今天/阻塞） |
| Sprint Review | 版本演示会（可玩版本showcase） |
| Retrospective | 版本复盘会 |

### 游戏敏捷的特殊挑战
1. **创意不确定性**：做出来才知道好不好玩，需要频繁原型→测试→迭代
2. **长管线依赖**：美术/动画管线周期长，难以在单个Sprint内闭环
3. **技术债务**：为了赶版本欠下的技术债，需要专门的"技术Sprint"偿还
4. **跨职能协作**：策划/程序/美术/QA节奏不同

### 推荐的游戏敏捷模式
```
2周Sprint + 功能开关(Feature Flag) + 每周内部Playtest

Sprint 1 Week 1: 需求评审 + 核心开发
Sprint 1 Week 2: 联调 + QA + 内部测试
Sprint Review: 可玩Demo演示 + 反馈收集
Sprint Retrospective: 流程优化 + 技术债清理
```

### 看板管理
```
待办(Backlog) → 本迭代(Sprint) → 进行中(In Progress) → 
待测试(QA) → 待验收(Review) → 已完成(Done)
```
- WIP限制：每个开发者同时进行中不超过2个任务
- 阻塞可视化：卡住的任务标红+指定owner

## 案例
- **Supercell**：Cell制（小团队，2周Sprint，不好就砍）
- **拳头游戏**：Strike Team模式（功能小队，从概念到上线全权负责）

## 检查清单
- [ ] 是否有固定的迭代节奏
- [ ] 每日是否有同步机制
- [ ] 迭代结束是否有可演示的成果
- [ ] 是否有定期复盘和持续改进

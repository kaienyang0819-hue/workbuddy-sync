# 跨职能团队沟通与冲突管理

## 核心观点
游戏开发中最大的摩擦不在技术难题，而在人与人之间的沟通。策划和程序为可行性争执、美术和策划为风格争执、QA和所有人为Bug优先级争执——这些冲突不可避免，但可以建设性地管理。

## 方法论

### 常见冲突类型
| 冲突 | 双方 | 核心矛盾 |
|------|------|----------|
| 可行性争执 | 策划 vs 程序 | "能不能做" vs "值不值得做" |
| 品质争执 | 策划/美术 vs PM | "做到最好" vs "准时发布" |
| 优先级争执 | 策划A vs 策划B | 不同系统争抢开发资源 |
| 修复争执 | QA vs 开发 | BUG严重程度定义不一致 |

### 建设性沟通框架：DESC法
- **D(Describe)**：客观描述情况，不带评判
- **E(Express)**：表达感受和影响
- **S(Specify)**：提出具体请求
- **C(Consequence)**：说明积极后果

示例："这个系统的设计文档缺少异常处理说明（D），这导致开发时需要反复确认（E），希望在文档中增加异常处理章节（S），这样开发效率能提升30%以上（C）"

### 跨职能协作最佳实践
1. **统一语言**：建立团队术语表，避免同一个词不同理解
2. **可视化进度**：物理看板/线上看板，所有人看同一块板
3. **定期同步**：每日站会（15分钟）+ 每周同步会（1小时）
4. **非暴力沟通**：观察→感受→需要→请求

### 决策升级机制
```
Level 1: 当事人直接沟通（5分钟可解决的）
Level 2: 小组讨论（需要多方权衡的）
Level 3: Lead决策（跨组优先级冲突）
Level 4: 制作人拍板（涉及方向性决策）
```

## 检查清单
- [ ] 是否有定期的跨职能同步机制
- [ ] 冲突是否在合适的层级解决
- [ ] 决策结果是否有记录
- [ ] 团队沟通氛围是否健康

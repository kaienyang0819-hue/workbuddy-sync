# 上线发布与灰度策略

## 核心观点
游戏版本上线不是"把包发出去"这么简单。从灰度放量到全量发布，从热更新到强更新，需要一套完整的发布策略来控制风险。"慢即是快"——宁可多花2天灰度，也不要全量翻车。

## 方法论

### 发布策略矩阵
| 策略 | 适用场景 | 风险级别 |
|------|----------|----------|
| 灰度发布 | 大版本/新功能 | 低（可控回滚） |
| 全量推送 | 热修复/紧急BUG | 中（影响全部用户） |
| 功能开关 | 新功能测试 | 低（随时关闭） |
| A/B分流 | 方案对比验证 | 低（对照实验） |

### 灰度放量标准流程
```
1% → 监控1小时 → 5% → 监控4小时 → 20% → 监控24小时 → 50% → 监控24小时 → 100%

每阶段检查：
□ Crash率是否上升
□ 核心指标是否异常（DAU/付费/留存）
□ 客服工单是否激增
□ 舆情是否有大面积负面
```

### 回滚预案
- **热更新回滚**：下发上一版本配置/脚本
- **客户端回滚**：强制更新到修复版本
- **服务端回滚**：切回旧版服务+数据兼容性检查
- **数据回滚**：如果涉及数据变更，准备回滚脚本

### 发布Checklist
- [ ] 版本包是否通过全量测试
- [ ] 灰度计划是否确定（放量比例+时间）
- [ ] 回滚方案是否就绪
- [ ] 运维值班人员是否到位
- [ ] 公告/补偿方案是否准备好
- [ ] 监控大盘是否配置好

## 检查清单
- [ ] 是否有灰度发布计划
- [ ] 每阶段的检查指标是否明确
- [ ] 回滚方案是否测试过
- [ ] 是否有发布后值班机制

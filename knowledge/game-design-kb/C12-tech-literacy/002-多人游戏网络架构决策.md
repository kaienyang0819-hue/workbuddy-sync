## 核心观点

1. **网络架构选择直接决定了战斗设计空间** — 这不是程序的事，策划必须参与决策
2. **没有完美方案，只有适合品类的方案** — MOBA用帧同步，MMO用状态同步，各有道理
3. **延迟是多人游戏体验的最大敌人** — 所有网络优化的目标都是"让玩家感觉不到延迟"

## 帧同步vs状态同步深度对比

| 维度 | 帧同步 | 状态同步 |
|------|--------|---------|
| **计算位置** | 全在客户端 | 核心在服务器 |
| **网络传输** | 只传输入指令(小) | 传状态快照(大) |
| **一致性** | 天然一致(确定性) | 需要额外同步 |
| **安全性** | 差(客户端可作弊) | 好(服务器权威) |
| **断线重连** | 困难(需回放) | 简单(发快照) |
| **回放/录像** | 天然支持 | 需额外记录 |
| **玩家数** | 适合少人(2-10) | 适合多人(100+) |
| **延迟敏感度** | 一人卡全场 | 可独立处理 |

### 品类选型矩阵

| 品类 | 推荐方案 | 原因 |
|------|---------|------|
| MOBA/RTS | 帧同步 | 需要精确一致、回放功能 |
| 格斗 | 帧同步+回滚 | 帧精确判定是核心 |
| FPS | 状态同步+延迟补偿 | 多人/反作弊/断线重连 |
| MMO | 状态同步 | 大规模玩家+服务器权威 |
| 大逃杀 | 状态同步 | 100人同场 |
| 休闲/回合 | 状态同步 | 简单可靠 |

### 策划必须理解的延迟概念

- **RTT(往返延迟)**: 从发送到收到回复的时间，<100ms体验好，>200ms明显卡
- **延迟补偿**: 服务器"回溯时间"判断命中（FPS射击核心技术）
- **预测回滚**: 客户端先预测执行，服务器不一致时回滚（格斗游戏核心）
- **插值平滑**: 在两个状态快照间做动画过渡，让移动看起来流畅

## 设计检查清单

- [ ] **架构选型**: 是否与程序确认了网络架构？是否匹配品类？
- [ ] **延迟预算**: 核心操作在200ms RTT下是否仍然可接受？
- [ ] **作弊预防**: 关键数值是否在服务器验证？
- [ ] **断线体验**: 断线重连后玩家体验是否可接受？

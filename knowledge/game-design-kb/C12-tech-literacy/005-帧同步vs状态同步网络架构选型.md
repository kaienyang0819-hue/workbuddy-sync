## 核心观点

多人游戏的核心技术挑战是"如何让所有玩家看到一致的世界"。三大同步方案各有适用场景，策划必须理解其trade-off才能做出合理的设计决策。

### 三大同步方案对比

| 维度 | 状态同步 | 帧同步 | 客户端预测 |
|------|----------|--------|------------|
| **原理** | 服务端计算→广播状态 | 服务端排序指令→客户端各自计算 | 客户端先行预测→服务端校正回滚 |
| **延迟感知** | 明显（200ms+） | 明显（100ms+） | 近乎0延迟 |
| **带宽消耗** | 高（全状态广播） | 低（只传指令） | 中等 |
| **安全性** | 高（服务端权威） | 低（客户端计算） | 中等 |
| **断线恢复** | 容易 | 复杂（需重播） | 中等 |
| **适用品类** | 回合制/策略/棋牌 | RTS/MOBA | FPS/动作 |
| **开发成本** | 低 | 中 | 高 |

### 关键技术概念

**状态同步**：客户端→指令→服务端→计算→广播全局状态。安全但延迟大。
**帧同步**：服务端只做指令排序，客户端各自运行游戏逻辑。需保证确定性（浮点一致、随机数种子一致）。
**客户端预测**：四步循环——立即响应→本地预测→服务端校正→回滚机制。玩家感知0延迟。

### 混合方案（业界主流）
- **核心操作**：客户端预测（射击、移动）
- **关键事件**：状态同步（击杀、拾取）
- **环境元素**：帧同步（小兵AI、技能弹道）

## 方法论

### 策划选型决策树
```
玩家数量 > 100? → 状态同步（带宽优化）
├─ 实时性要求极高? → 客户端预测
├─ 需要完美回放? → 帧同步
├─ 安全性优先? → 状态同步
└─ 混合需求? → 核心预测 + 事件状态同步
```

### 策划需要注意的设计约束
1. **帧同步项目**：禁止使用非确定性逻辑（float运算误差、Dictionary遍历顺序等）
2. **状态同步项目**：服务端计算压力大，技能数值验证需服务端完成
3. **客户端预测项目**：需要设计"回滚补偿"视觉效果（如死亡回放校正）

## 案例分析

| 游戏 | 同步方案 | 策划影响 |
|------|----------|----------|
| 王者荣耀 | 帧同步 | 10人确定性同步，断线重连需追帧 |
| CSGO/瓦罗兰特 | 客户端预测+状态同步 | 128tick高频服务器，命中判定服务端权威 |
| 文明系列 | 状态同步 | 回合制天然适配，大量AI在服务端计算 |
| 守望先锋 | 客户端预测+服务端回滚 | 著名的"Favor the shooter"命中补偿 |
| 星际争霸2 | 帧同步 | 完美回放系统，但断线=GG |

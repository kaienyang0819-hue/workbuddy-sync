## 核心观点

热更新是GaaS游戏的生命线——不需要玩家重新下载安装包就能更新游戏内容。策划必须理解热更新的能力边界，才能设计出"可热更"的内容。

### 热更新类型

| 类型 | 可更新内容 | 策划影响 |
|------|-----------|----------|
| **资源热更** | 贴图/模型/音效/UI | 新皮肤/活动素材可热更 |
| **配置热更** | 数值表/策划配置 | 数值调整/活动配置可热更 |
| **脚本热更** | Lua/Python/C#(IL2CPP) | 逻辑修复/新玩法可部分热更 |
| **代码热更** | 原生C++代码 | 通常不可热更→需发版 |

### 策划配置表设计原则
1. **数据驱动**：一切可变内容走配置表，不写死在代码中
2. **结构稳定**：配置表结构（列定义）需发版，数据（行内容）可热更
3. **引用完整**：资源引用需确保热更包包含所有依赖
4. **版本兼容**：新版配置需兼容旧版客户端

### 热更新策划工作流
```
策划填写配置表 → SVN/Git提交 → 构建工具打包
    → 发布到CDN → 客户端启动时检查更新
    → 下载差异包 → 热加载新内容
```

## 方法论

### "可热更设计"检查
- **新活动**：活动逻辑是否可通过配置表驱动？还是需要新代码？
- **新角色**：技能效果是否走通用技能框架？还是需要特殊逻辑？
- **数值调整**：所有数值是否都在配置表中？有没有写死的常量？
- **UI变更**：新界面是否使用现有UI框架？还是需要新的UI组件？

### 平台审核约束
| 平台 | 审核周期 | 热更限制 |
|------|----------|----------|
| iOS | 1-3天 | 禁止代码热更（JSPatch被封） |
| Android | 几小时 | 较宽松 |
| Steam | 即时 | 无限制 |
| 主机 | 3-7天 | 严格审核 |

## 案例分析

| 场景 | 可热更 | 需发版 |
|------|--------|--------|
| 修改英雄伤害值 | ✅ 配置表热更 | |
| 新增一个活动页面 | ✅ 如果用通用模板 | ❌ 如果需新UI组件 |
| 修复技能bug | ✅ 如果是Lua脚本 | ❌ 如果是C++逻辑 |
| 新增英雄 | ✅ 模型+配表+通用技能 | ❌ 全新技能机制 |
| 更换开屏界面 | ✅ 资源替换 | |

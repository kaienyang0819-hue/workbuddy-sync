# AI event radar weekly

## When to use

- 用户要求每周、定期或滚动追踪 AI 大事件、AI 应用 Case、行业变化或 Agent 工具更新。
- 用户强调需要扩展 AI 能力/应用视野，尤其希望从社区发现新颖案例。
- 不适用于只需要模型发布新闻、单一公司动态或游戏行业专项情报的任务。

## Core principle

> 社区是 Case 的主发现源；官方材料只负责确认模型/产品或事实，不得用官方发布替代社区 Case。

Case 的目的只是拓展视野，不是评估可用性。收录时只说明：谁在用 AI 做什么、AI 扮演什么角色、新颖点、来源和可信度。不得把流程、效率、效果、限制、失败复盘或游戏迁移性设为收录门槛。

## Source network

### Community discovery network (mandatory)

1. 海外讨论：X、Reddit、Hacker News。
2. 开发者与产品：GitHub Trending / Releases / Discussions、Product Hunt。
3. 中文真实使用：B站、小红书、即刻、知乎、V2EX。
4. 视频与创作者：YouTube、B站及创作者博客。

每轮必须至少覆盖：
- 1 个海外讨论源；
- 1 个开发者/项目源；
- 1 个中文内容社区源。

若 X、Reddit、小红书等需要登录、授权或遭遇风控，必须在报告开头标注缺失渠道，不能用官方新闻填补并假装覆盖了社区。

### Verification network

对 P0/P1 事件补充至少一种核验：当事人原帖、项目仓库、公开演示、产品页面、公司公告、监管文件或独立可靠报道。保留：
- 发现源：最先发现 Case 的社区链接；
- 事实源：确认发生的原始材料；
- 评价源：可选，独立讨论或反方信息。

## Steps

1. 设定滚动窗口：执行日期向前14天；按事件/Case去重，而非按链接去重。
2. 先跑社区发现：使用“showcase”“built with AI”“AI workflow”“using AI for”“agent workflow”“AI 实战”“用 AI 做”“AI 落地案例”等组合词；同时针对本周热门工具、行业和创作者扩展关键词。
3. 把帖子、视频、项目、讨论合并成候选 Case，记录链接、日期、作者/组织、平台和一句话摘要。
4. 分别检索模型能力、行业/公司、Agent 工具更新，作为背景和热点信号，不能挤占 Case 栏目。
5. 对候选补充事实源，并标注可信度：实锤、强推断、推测、猜测。
6. 按“热点度 + 视野增量”给优先级：
   - P0：高热点且高视野增量，或明显刷新AI新用法的低热度案例；
   - P1：热点或视野增量有一项突出；
   - P2：有意思但信息/影响暂不足；
   - 风声池：单一爆料或待验证信号。
7. 先写 P0/P1，再写 P2 和风声池。输出不得设置类别配比，也不得因与游戏无关而过滤。

## Output format

1. 本周先看：3-5条横向变化。
2. P0｜本周必看：模型、Case、行业或Agent变化混排，按优先级而非类别排序。
3. 本周AI新用法 / Case：必须以社区发现源为主体；每条写“Case是什么 / AI在做什么 / 新颖点 / 来源与状态”。
4. P1/P2重要动态：按模型、行业、Agent索引归档。
5. 风声池：传闻与未证实信息独立呈现。
6. 覆盖边界：明确本轮已接入与未接入的社区渠道。

## Pitfalls

- 不要把官方模型公告写成“具体 Case”。
- 不要将新闻转载、营销稿或无出处截图当 Case。
- 不要因为案例缺少效率、ROI、技术流程或失败信息而剔除。
- 不要强行写“对游戏的启发”；仅在天然相关时补充。
- 不要将热点度与可信度混为一谈：高热度传闻仍只能是风声池。
- 社区渠道不可用时，先报告缺口并请求授权/连接；不要以低质量网页搜索替代。

## Verification

交付前逐项检查：
- 是否覆盖至少三个不同类型的社区源？
- Case 栏目是否以社区发现源为主，而非官方发布？
- 每个 P0/P1 是否包含发现源和至少一个事实源？
- 是否明确标记所有未授权、被风控或未覆盖的平台？
- 是否没有把效率/可用性/游戏迁移性当作 Case 门槛？

# 系统策划文档标准格式生成器

该技能提供标准化的策划文档生成API和样式规范,**支持根据实际需求动态生成不同类型系统的策划文档**。

## 核心理念

- **通用性** - 提供标准API,适用于各类系统策划文档
- **灵活性** - 根据需求动态构建模块,不限制固定内容
- **可扩展** - 支持新增模块类型
- **规范性** - 统一的样式、格式、结构标准
- **⚠️ 信息完整性** - 源文档/输入中的每一条规则细节都必须保留,不得概括或省略

## ⚠️ Gotchas（已知陷阱）

> 以下是实际使用中反复出现的错误模式。**这些是最高优先级的提醒**——如果你只看一个段落，看这个。

### 源文档读取类

| # | 陷阱 | 正确做法 |
|---|------|----------|
| G1 | ❌ 源文档多页签时只读了第一页就开始生成 | ✅ 必须逐页签完整读取，一个都不能漏 |
| G2 | ❌ 单页签行数多时只读了前 N 行就认为够了 | ✅ 超过 100 行分批读取直到最后一行 |
| G3 | ❌ xlsx 图片只在 `xl/media/` 路径下找 | ✅ 还需尝试 `xl/drawings/media/` 路径，需多路径尝试 |
| G4 | ❌ xmind 文件当普通文件读取失败就放弃 | ✅ xmind 是 zip 格式，解压后读取 `content.json` |

### 内容生成类

| # | 陷阱 | 正确做法 |
|---|------|----------|
| G5 | ❌ 把"规范化"理解成"精简化"，用概括语句替代具体规则 | ✅ **信息完整性 > 一切**，源文档的每条规则/数值/文案必须原文保留 |
| G6 | ❌ 规则三件套机械填空，大量空的「2、交互图」占位 | ✅ 纯逻辑规则只写「1、规则说明」即可，三件套按需简化 |
| G7 | ❌ 源文档有弹窗文案/提示语，生成时只写了"有弹窗提示" | ✅ 文案必须原文保留，用 `is_highlight=True` 标记 |
| G8 | ❌ 源文档的 P0/P1/P2 优先级标记被丢掉了 | ✅ 优先级标记必须保留在规则说明中 |
| G9 | ❌ 内容量很大的子系统挤在一个模块里，导致结构扁平 | ✅ 大子系统（如赠礼/装扮/训练）各自拆为独立一级标题 |

### API 调用类

| # | 陷阱 | 正确做法 |
|---|------|----------|
| G10 | ❌ 调用函数时手动传了 `col` 参数导致列号错位 | ✅ **所有函数已固定列号，调用时不传 col 参数** |
| G11 | ❌ 忘记在每个规则的「1、规则说明」前调用 `reset_auto_number()` | ✅ 每个新规则的规则说明前必须重置序号 |
| G12 | ❌ 用手写循环来创建表格 | ✅ 统一用 `add_table()` 一站式创建，自动处理样式和交替行 |
| G13 | ❌ 图片嵌入时不区分场景，全用同一个函数 | ✅ 交互图用 `add_image_in_rule()`(E列)，数据图用 `add_image_under_title()`(B列) |

### 完成度检查类

| # | 陷阱 | 正确做法 |
|---|------|----------|
| G14 | ❌ 生成完直接交付，不做信息量对比 | ✅ 必须统计源文档内容行数 vs 生成文档 `add_content` 调用数，低于 70% 说明严重丢失 |
| G15 | ❌ 页签3/4 是空的或只有标题 | ✅ 页签2中每个引用的配置表，页签3必须有对应表格；功能事件在页签4必须有打点 |
| G16 | ❌ 源文档的子标题/功能点在生成文档中找不到对应的 rule_title | ✅ 每个源文档功能点必须对应至少一个 rule_title，一一映射 |

> **持续更新**：每次使用该 Skill 踩到新坑，都会追加到此表中。

## ⚠️ 信息完整性原则（最高优先级）

**规范化 ≠ 精简化。** 策划文档的规范化是改善格式和结构,不是删减内容。

### 必须遵守的规则:

1. **源文档中的每一条规则说明、每一个条件、每一个数值都必须保留**
   - 源文档写了"点击训练,则文本提醒：已指派AI角色XX前往训练!" → 必须原文写入
   - 源文档写了"时间最小单位为1hour,向上取整" → 必须保留这个细节
   
2. **不得用概括性语句替代具体规则**
   - ❌ 错误："训练有时段限制和人数上限" （丢失了所有细节）
   - ✅ 正确：逐条列出每一个限制条件、数值、文案

3. **规则说明中的每一行都应该是一个 `add_content()` 调用**
   - 源文档中用 `>` `--` `①②③` 标记的每一条都是独立的规则点
   - 每条用 `add_content(auto_number=True)` 单独一行

4. **源文档中的图片必须保留并嵌入**
   - 源文档（xlsx/xmind等）中包含的交互图、界面截图、数据图表，必须提取并嵌入到对应规则的「2、交互图」位置
   - 提取流程：解压源文件 → 解析drawing关系 → 提取图片到本地 → 用 `add_image_in_rule()` 嵌入
   - 没有图片文件时才用文字占位 `[嵌入：xxx.png]`

5. **文案/提示文本必须保留原文**
   - 弹窗文案、提示语、按钮文字等必须完整保留
   - 使用 `add_content(is_highlight=True)` 标记重要文案

6. **优先级标记（P0/P1/P2）必须保留**

7. **数值参数必须保留**
   - 时长、上限、刷新时间、品质、加成值等

8. **源文档有多页签/子模块时，必须逐页签完整读取**
   - 不能只读前N行就开始生成，必须读完所有相关页签的全部行
   - 单页签超过100行时，分批读取直到读完

### 信息量对比检查（生成后必做）:
1. 统计源文档各页签的有效内容行数
2. 统计生成文档页签2的 `add_content` 调用次数
3. 如果生成文档的内容行数低于源文档的 **70%**，说明有严重信息丢失，必须补充
4. 重点检查：源文档中的每个子标题/功能点是否都对应了生成文档中的一个 rule_title

## ⚠️ 层级缩进规范（必须遵守）

文档内容按列号严格对齐,不得随意修改 col 参数:

| 列 | 用途 | 对应函数 |
|----|------|----------|
| **A列(1)** | 留空 | — |
| **B列(2)** | 一级标题/二级标题/三级标题/单行内容/表格标题 | `add_title_1` `add_title_2` `add_title_3` `add_single_line` `add_table_title` |
| **C列(3)** | 规则标题 | `add_rule_title` |
| **D列(4)** | 标签 / 待决策项 | `add_label` `add_pending_item` |
| **E列(5)** | 正文内容 | `add_content` |

**所有函数已固定列号,调用时不需要传 col 参数。**

层级示意:
```
A    B                C              D              E
     【一级标题】     ←合并A~E
     二级标题
     三级标题
     单行内容...
                      规则1：xxx
                                     1、规则说明
                                                    1. 具体内容...
                                                    2. 具体内容...
                                     2、交互图
                                                    [嵌入：xxx.png]
                                     3、表格配置
                                                    → 配置表.xxx(页签3-表1)
                      规则2：xxx
                                     1、规则说明
                                     ...
                                     待决策：xxx？
```

## 使用工作流

### 1. 接收需求
接收用户输入，可能是：
- 文字描述的系统功能
- 图片/截图中的策划内容
- xmind脑图（解压后读取content.json）
- 现有文档的优化需求

### 2. 分析内容
- 提取所有功能点和关键词
- 对照「通用模块菜单」识别需要包含的模块
- 判断每个模块用概述结构还是规则结构
- 梳理模块间的逻辑顺序

### 3. 动态构建
- 页签1：填充文档信息（固定结构）
- 页签2：按模块顺序逐一构建（每个模块一个一级标题）
- 页签3：为页签2中引用的每个配置表创建对应表格
- 页签4：为系统功能设计对应的事件打点

### 4. 生成文档
- 保存到「环境配置」中指定的输出路径
- 文件名格式：`{系统名称}策划案.xlsx`

---

## 注意事项

1. 所有文字使用微软雅黑字体
2. 标题和正文都不换行
3. **不要手动传 col 参数**, 层级由函数固定
4. 规则三件套可按实际情况简化（见内容规范）
5. 每个规则的"1、规则说明"前调用 `reset_auto_number()`
6. 表格用 `add_table()` 一站式创建, 避免手写循环
7. 文件输出路径见「环境配置」章节
8. 规则标题命名遵循「规则标题命名规范」
9. 子层级内容使用 `add_content(is_sub=True)` 表示缩进

### 页签2: 设计内容（动态构建）

#### 通用模块菜单（按需选用）

以下是系统策划文档的标准模块列表。根据输入需求判断哪些模块需要包含，**不是每个文档都要写全部模块**：

| 模块 | 何时需要 | 内容结构 |
|------|----------|----------|
| **需求背景** | 几乎所有文档都需要 | 概述结构：趋势/现状/痛点/数据支撑 |
| **设计目的** | 几乎所有文档都需要 | 规则结构：逐条列出设计目标 |
| **系统概述** | 系统较复杂、涉及多子系统时 | 概述结构：整体框架、功能模块列表、与其他系统的关系 |
| **界面入口** | 有多个入口/功能开启条件时 | 规则结构：各入口位置+触达路径+开启条件 |
| **核心玩法/流程** | 有具体功能规则需要程序实现时 | 规则结构：规则三件套（可拆分多个子功能，每个子功能一个一级标题） |
| **角色/对象信息** | 涉及角色属性、信息展示、3D形象时 | 规则结构：信息展示/属性体系/形象切换 |
| **聊天/社交互动** | 涉及聊天功能、话题库、消息通知时 | 规则结构：聊天入口/话题机制/消息过滤/通知 |
| **数值设计** | 涉及等级/经验/概率/公式时 | 概述结构 + 配置表引用 |
| **成长体系** | 涉及好感度/亲密度/等级成长时 | 规则结构：成长维度/获取途径/每日上限 |
| **奖励设计** | 涉及奖励投放、产出消耗时 | 规则结构：奖励类型/投放策略/领取流程 |
| **界面交互** | 有UI入口/界面流程变更时 | 规则结构：局内/局外分别描述 |
| **新手引导** | 有首次进入/引导流程时 | 规则结构：触发条件/引导步骤/完成条件 |
| **赛季/周期** | 涉及赛季重置、周期规划时 | 概述结构：时间线/节奏规划 |
| **社交/排行** | 涉及排行榜、社交传播时 | 规则结构：排行规则/奖励 |
| **匹配策略** | 涉及匹配机制、组队规则时 | 规则结构：匹配维度/限制/安全 |
| **AI投放** | 涉及AI对局、温暖局策略时 | 规则结构：投放条件/AI能力 |
| **处罚策略** | 涉及惩罚、行为规范时 | 规则结构：处罚对象/手段/梯度 |
| **安全/反作弊** | 涉及防刷、风控时 | 规则结构：识别/应对 |
| **版本兼容** | 涉及拆包、跨版本差异时 | 规则结构：兼容方案 |
| **面板开关控制** | 功能需要开关控制时 | 规则结构：开关配置 |
| **待决策项汇总** | 有未确定的设计问题时（放最后） | 待决策项列表 |

**重要**：当源文档的某个子系统内容量很大（如多个功能模块各自有详细规则），应将该子系统拆分为独立的一级标题，而不是挤在一个模块里。例如：AI角色养成系统中的"赠礼""装扮""训练"应各自成为独立的一级标题模块。

#### 构建决策流程

收到需求后，按以下步骤决定文档结构：

```
Step 1: 完整读取输入
        - 文字/图片: 直接分析
        - xmind: 解压→读取content.json
        - xlsx源文档: 逐页签完整读取（不得遗漏任何页签）
        - 每个页签必须读到最后一行，超过100行的分批读取
        
Step 2: 逐页签/逐模块建立内容映射
        - 列出源文档每个页签/模块的功能点清单
        - 对照通用模块菜单，确定每个功能点对应的模块
        - 一个源文档页签可能对应一个或多个一级标题
        
Step 3: 确定模块顺序（一般按上表从上到下，待决策项放最后）

Step 4: 判断每个模块用「概述结构」还是「规则结构」（见下方指引）

Step 5: 逐模块构建页签2
        - 每个功能点的每一条规则都必须转化为 add_content 调用
        - 同步提取图片并嵌入
        
Step 6: 同步构建页签3（源文档中的配置表/示例数据搬过来）和页签4（事件打点）

Step 7: 完整性自检（见信息量对比检查）
```

#### 概述结构 vs 规则结构的选择

| 用概述结构 | 用规则结构 |
|-----------|-----------|
| 背景描述（为什么做） | 具体功能规则（怎么做） |
| 设计目标列举 | 需要程序实现的逻辑 |
| 参数/段位罗列 | 有对应交互图的功能 |
| 时间线/节奏规划 | 有对应配置表的功能 |
| 竞品分析 | 处罚/匹配/AI等明确策略 |

**简单判断**：如果一个模块需要「交互图」和「配置表」，就用规则结构；否则用概述结构。

概述结构写法:
```python
row = add_title_1(ws2, row, '【模块名】')
row = add_title_2(ws2, row, '子主题')
row = add_single_line(ws2, row, '描述内容...')
```

规则结构写法:
```python
row = add_title_1(ws2, row, '【模块名】')
row = add_rule_title(ws2, row, '规则1：xxx')
row = add_label(ws2, row, '1、规则说明')
reset_auto_number()
row = add_content(ws2, row, '具体规则', auto_number=True)
row = add_label(ws2, row, '2、交互图')
row = add_content(ws2, row, '[嵌入：xxx.png]', is_comment=True)
row = add_label(ws2, row, '3、表格配置')
row = add_content(ws2, row, '→ 配置表.xxx（页签3-表N）', is_link=True)
```

### 页签3: 数值表格设计

使用 `add_table()` 一站式创建。根据系统类型选用合适的表头模板：

#### 常见表格 headers 模板

| 表格类型 | headers |
|----------|---------|
| **通用配置表** | `['字段名', '类型', '说明', '示例值']` |
| **开关配置表** | `['开关ID', '开关名称', '适用平台', '默认值', '说明']` |
| **奖励配置表** | `['奖励ID', '奖励类型', '奖励内容', '数量', '获取条件']` |
| **段位配置表** | `['段位ID', '段位名称', '最低分数', '最高分数', '子段位数']` |
| **匹配配置表** | `['段位范围', '匹配时间(s)', '扩段速度', '组队限制']` |
| **处罚配置表** | `['违规类型', '处罚手段', '扣分值', '禁赛时长', '累计递增']` |
| **商店配置表** | `['商品ID', '商品名称', '货币类型', '价格', '限购数量']` |

```python
row = 1
row = add_title_1(ws3, row, '【数值表格设计】')
row = add_table(ws3, row, '表1-配置表名称',
    headers=['字段名', '类型', '说明', '示例值'],
    data=[
        ['field_id', 'int', '字段ID', '1'],
        ['field_name', 'string', '字段名称', '示例'],
    ])
row += 1  # 表间空行
row = add_table(ws3, row, '表2-另一个配置表', ...)
```

### 页签4: tlog及打点设计

## 内容规范

### 规则三件套（规则结构）

**完整三件套**（有交互图或配置表时使用）：
1. **1、规则说明** — 具体规则描述,使用 `auto_number=True` 自动递增
2. **2、交互图** — 图片引用或嵌入,使用 `add_image_in_rule()` 或 `is_comment=True`
3. **3、表格配置** — 配置表引用,使用 `is_link=True`

**简化规则**（三件套不是死规矩）：
- 如果规则有实际交互图/截图 → 完整三件套
- 如果规则有对应配置表但无交互图 → 写「1、规则说明」+「3、表格配置」，省略「2、交互图」
- 如果规则是**纯逻辑**（无交互图、无配置表） → 只写「1、规则说明」即可
- 避免大量无意义的 `[嵌入：xxx.png]` 占位,提升文档可读性

### 图片处理策略

用户提供的图片按类型分三种处理方式：

| 图片类型 | 处理方式 | 嵌入位置 |
|----------|----------|----------|
| **交互流程图/界面截图** | 嵌入文档 + 提取内容写规则 | 规则内「2、交互图」→ `add_image_in_rule()` |
| **数据图表/调研截图** | 嵌入文档 + 提取关键结论 | 模块标题下方 → `add_image_under_title()` |
| **xmind/脑图截图** | 仅提取内容,不嵌入 | 不嵌入,内容写入对应模块 |

使用示例:
```python
# 场景1: 在规则的交互图位置嵌入
row = add_label(ws2, row, '2、交互图')
row = add_image_in_rule(ws2, row, 'G:/project_output/images/flow_chart.png',
                        description='图1：功能触发流程')

# 场景2: 在模块标题下方嵌入数据图
row = add_title_2(ws2, row, '用户数据')
row = add_image_under_title(ws2, row, 'G:/project_output/images/user_data.png',
                            description='图：团竞用户流失趋势')

# 场景3: 没有实际图片文件时,用文字占位
row = add_label(ws2, row, '2、交互图')
row = add_content(ws2, row, '[嵌入：xxx流程图.png]', is_comment=True)
```

**工作流程**: 当用户提供图片时:
1. 先用多模态识别图片内容
2. 将图片保存到 `G:/project_output/images/` 目录
3. 提取图片中的文字/数据写入对应的规则说明
4. 调用 `add_image_in_rule()` 或 `add_image_under_title()` 嵌入图片

### 何时用什么函数

| 内容类型 | 函数组合 | 示例场景 |
|----------|----------|----------|
| 背景/趋势/现状描述 | `add_title_2` + `add_single_line` | 需求背景、竞品分析 |
| 设计目标列举 | `add_rule_title` + `add_label` + `add_content(auto)` | 设计目的（逐条） |
| 具体功能规则 | `add_rule_title` + 三件套(可简化) | 核心玩法、匹配策略 |
| 规则中的子层级 | `add_content(is_sub=True)` | 条件分支、枚举选项 |
| 参数/段位/数值罗列 | `add_title_2` + `add_single_line` | 段位划分、基础参数 |
| 时间线/节奏规划 | `add_title_2` + `add_single_line` | 赛季规划、版本计划 |
| 方案对比（多方案） | `add_single_line` 逐条描述 | 方案一/方案二 |
| 配置表数据 | `add_table()` | 页签3/4 的所有表格 |
| 未确定的设计问题 | `add_pending_item` | 待决策项汇总 |

### 规则标题命名规范

规则标题是文档的"目录骨架"，命名质量直接影响可读性：

```
格式：「规则N：动宾短语」
好的：规则3：训练状态冲突处理
好的：规则1：赠礼入口与触达路径
差的：规则1：基础功能（太模糊）
差的：规则2：当用户在大厅界面点击训练按钮时的处理（太长）
```

- 控制在 **≤15个中文字**
- 使用**动宾结构**（如"处理""配置""显示""计算"）
- 同一模块内按逻辑顺序：入口 → 功能说明 → 界面 → 异常处理 → 结算/流水

## 一、格式总览

`reviews/review.md` 是专家评审模块的唯一产出文件。它包含一个或多个专家的审查报告，以及一个综合摘要。

## 二、完整格式定义

### 2.1 单专家报告时

```markdown
# 专家评审报告

## 审查信息
- **审查类型**：[客户端 / 服务器 / UI / 策划设计]
- **被审查文档**：requirements.md
- **被审查内容**：[文档标题] requirements.md
- **输出智能体**：[小策 / 小克 / 小侯 / 小绘]
- **整体评价**：🟢 通过 / 🟡 有条件通过 / 🔴 需要重大修改

## 🔴 P0 - 致命问题（必须修改后才能推进）

**[Q-01] [问题标题]**
- 📍 位置：[章节路径，如：匹配系统 > 赛季机制 > 赛季重置规则]
- ❓ 质疑：[具体问题描述]
- 💥 影响：[不改会导致什么后果]
- 💡 建议：[改进方向或具体建议]

**[Q-02] [问题标题]**
- 📍 位置：...

- 💡 建议：...
```

## 三、字段说明

### 3.1 问题等级定义

| 等级 | 含义 | 对定稿的影响 |
|------|------|-------------|
| 🔴 P0 | 致命问题 | **阻塞定稿**，必须修改后才能推进 |
| 🟡 P1 | 严重问题 | **强烈建议修改**，不阻塞定稿但风险高 |
| 🟢 P2 | 一般问题 | 建议优化，不影响定稿 |
| ℹ️ P3 | 微小建议 | 可选改进，不影响定稿 |

### 3.2 整体评价标准

| 评价 | 判定条件 |
|------|---------|
| 🟢 通过 | 无 P0，P1 ≤ 1 |
| 🟡 有条件通过 | 无 P0，P1 ≥ 2；或 P0 = 1 但影响可控 |
| 🔴 需要重大修改 | P0 ≥ 2；或 P0 = 1 且影响严重 |

### 3.3 质疑编号规则

- 编号格式：`Q-XX`（两位数字，01 开始）
- **全局递增**：整个报告中编号不重置，不同专家的编号接续
- 示例：策划审查 Q-01~Q-05，客户端审查 Q-06~Q-08

### 3.4 审查评分维度

各专家对应的评分维度：

| 专家 | 评分维度 |
|------|---------|
| 挑战策 | 玩法合理性、数值健康度、文档完整性、体验完整性、商业化平衡、落地可行性 |
| 挑战克 | 代码安全性、性能表现、架构合理性、平台兼容、代码规范、防御性编程 |
| 挑战侯 | 协议完整性、表结构合理性、数据安全、并发一致性、容灾恢复、性能承压 |
| 挑战绘 | 信息架构、操作可用性、一致性、异常态覆盖、适配兼容、动效合理性 |

### 3.5 问题状态

| 状态 | 含义 |
|------|------|
| ⏳ 待回应 | 等待策划回复 |
| ✅ 已解决 | 策划已修改，复核通过 |
| 🔄 修改中 | 策划已知悉，正在修改 |
| ⏸️ 搁置 | 有合理理由暂不修改 |

## 四、requirements.md 标注格式

P0/P1 问题标注回 `requirements.md` 时，使用以下格式：

```markdown
> ⚠️ **[专家Review Q-XX]** [问题简述] —— [P0/P1]，详见 reviews/review.md
```

标注插入到对应章节标题的下方（标题行之后、正文内容之前）。

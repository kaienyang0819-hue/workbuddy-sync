# 原则驱动设计（Principle-Driven Design）

只做一件事：**在动手设计前，先把方向、边界、验收标准钉死，再用它们当尺子校验后续所有工作。**

## 1. 定位与边界

- **上游于需求规格**：本技能产出"定位"（支柱 + 边界 + 验收），是需求规格化（reqspec）、开发、写文档的前置。
- **不是设计执行**：不画 UI、不写代码、不写完整需求文档。产出的是"想清楚的骨架"。
- **不是万能药**：目标单一清晰、试错成本低的小活，直接用，别走这套。

## 2. 元方法：八步链

支柱是"单一真相源"，后面每一步都引用它。

```
1 支柱      → 这功能/产品要解决什么、凭什么（3-5 个，可证伪、有张力）
2 反支柱    → 明确"这不是什么"（不做什么，与"是什么"同等重要）
3 目标排序  → 把支柱翻译成优先级排序的目标/指标
4 具体规则  → 把支柱落到可执行的规则
5 边界情况  → 穷举异常流、极端场景
6 验收标准  → 定义"做到什么程度算对"（可测）
7 需求拆解  → 把规则拆成可执行单元（可进 TAPD）
8 评审      → 用支柱当尺子，抓"前置依赖未定义 / 违反支柱 / 边界遗漏"
```

详细标准（支柱怎么写、验收怎么写、评审怎么判）见 `references/method-core.md`。
产品场景的落地模板见 `references/product-design-template.md`。

## 3. 三条硬原则

1. **支柱必须可证伪**："好用"不是支柱，"新用户 3 分钟能完成首次 X"才是。每个支柱要能回答"违反它是什么样"。
2. **支柱必须产生张力**：支柱之间打架处，就是这个设计真正的难点。不打架的支柱太含糊。
3. **评审必须抓"未定义的前置依赖"**：最值钱的产出，往往不是"方案对不对"，而是"有哪些前置条件还没定义、却决定了方案能不能落地"。

## 4. 三种使用路径（先判断用户意图，再走）

### A. 从零设计一个功能/产品
走完整八步。第 1 步支柱最重——先逼用户把"要什么、不要什么"说清楚，再往下推导。

### B. 只想定方向（还没到设计）
只走第 1-3 步（支柱 + 反支柱 + 目标排序），产出"方向定位"，不往下写规则。

### C. 评审一个已有方案/需求
走第 8 步：先提炼出方案的隐含支柱，再拿它当尺子抓漏洞、抓未定义的前置依赖。返回 verdict（通过 / 关注 / 驳回）+ 理由，不做修补。

## 5. 支柱的追问方式（第 1 步核心）

不要一次问完，逐条收敛：

1. 这功能**最核心**解决用户什么？一句话。
2. 如果只能做一件事，是什么？
3. **明确不做**什么？（最容易踩的坑）
4. 什么情况下会**失败**？（反推验收标准）
5. 两条支柱冲突时，谁优先？（暴露张力）

## 6. 评审 verdict 格式（第 8 步）

```
[通过 / 关注 / 驳回] —— 一句话结论
理由（每条对应一个支柱或一个前置依赖）
```

- **关注**：有非阻塞问题，列出即可，用户决定是否改
- **驳回**：违反支柱或有阻塞性前置未知，不推进

## 7. 产物默认

- 产出写到用户指定位置；未指定时写到 `G:\project_output\`，命名 `功能名_设计定位.md`
- 支柱、验收、评审三部分必须保留；其余步骤按路径 A/B/C 决定详略

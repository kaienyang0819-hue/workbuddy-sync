# 定稿归档

## 概述

将通过质量审查的需求规格说明书**定稿、版本化并归档**。生成一份干净的最终版文档，可直接用于开发团队参考或 AI 编码助手的上下文输入。

**核心原则：只有通过审查的文档才能定稿。**

## 何时使用

- 质量审查完成，CRITICAL 问题已全部解决
- 用户确认文档可以定稿
- 需要对已定稿文档进行版本更新

## 何时不使用

- 从未运行过 `reviewing` → 先审查
- 还有 CRITICAL 问题未解决 → 先修改再审查
- 文档还在频繁修改中 → 等稳定后再定稿

<HARD-GATE>
```
没有通过审查的文档不能定稿
```

定稿前必须检查：
1. `review-report.md` 是否存在
2. 报告中是否有未解决的 CRITICAL 问题
3. 如果有 → 拒绝定稿，引导用户先解决

唯一例外：用户明确说"我知道有 CRITICAL 问题，但我仍然要定稿"
→ 在定稿文档中添加风险声明
</HARD-GATE>

## 流程

### 第一步：定稿前检查

```markdown
## 定稿检查清单

### 前置条件
- [ ] requirements.md 存在且内容完整
- [ ] review-report.md 存在
- [ ] 所有 CRITICAL 问题已解决
- [ ] 所有 HIGH 问题已解决或用户明确搁置
- [ ] 无残留的 [待澄清] 标记（或用户明确搁置）

### 文档完整性
- [ ] 元信息完整（编号、版本、日期、状态）
- [ ] 至少 1 个 P1 用户故事
- [ ] 所有用户故事有验收场景
- [ ] 非功能需求有量化指标
- [ ] 术语表完整
- [ ] 变更历史已记录
```

### 第二步：生成最终版文档

基于 `requirements.md` 生成 `final-spec.md`，做以下处理：

1. **状态更新**：将元信息中的状态从"草稿"/"审查中"改为"已定稿"
2. **版本号确定**：
   - 首次定稿：v1.0
   - 小幅修改后重新定稿：v1.1, v1.2...
   - 重大变更（新增/删除用户故事）：v2.0, v3.0...
3. **清理残留标记**：
   - 已解决的 `[待澄清]` → 删除标记
   - 用户搁置的 `[待澄清]` → 转为 `[已知限制]` 并说明理由
4. **添加审查摘要**：在文档末尾添加审查通过记录
5. **生成文档摘要**：在文档开头添加 Executive Summary（3-5 句话概括）

### 最终文档结构

```markdown
# [功能名称] 需求规格说明书（定稿）

## Executive Summary
[3-5 句话概括整个需求的核心内容，供高层快速了解]

## 元信息
| 字段 | 值 |
|------|-----|
| 编号 | NNN |
| 版本 | v1.0 |
| 创建日期 | YYYY-MM-DD |
| 定稿日期 | YYYY-MM-DD |
| 状态 | ✅ 已定稿 |
| 审查评分 | X/100 |

[... 正文内容与 requirements.md 一致，但已清理 ...]

## 审查通过记录
| 轮次 | 日期 | 评分 | 结论 |
|------|------|------|------|
| 1 | YYYY-MM-DD | X/100 | 通过 |

## 已知限制
[用户明确搁置的待澄清项及其理由]
```

### 第三步：归档历史版本

如果这是一次版本更新（非首次定稿）：

1. 将旧版 `final-spec.md` 移动到 `specs/archive/<NNN>-<name>-v<old>.md`
2. 新版 `final-spec.md` 替代旧版
3. 在变更历史中记录本次变更

目录结构：

```
specs/
├── 001-用户认证/
│   ├── requirements.md      # 工作文档（可继续编辑）
│   ├── clarifications.md    # 澄清记录
│   ├── review-report.md     # 最新审查报告
│   └── final-spec.md        # 当前最终版 ← 开发团队看这个
└── archive/
    ├── 001-用户认证-v1.0.md  # 历史版本
    └── 001-用户认证-v1.1.md  # 历史版本
```

### 第四步：增量更新支持（Delta Spec）

当需要对已定稿的文档做增量更新时：

1. 在 `requirements.md` 中修改（标记变更类型）
2. 重新运行 `reviewing`
3. 重新运行 `finalizing`

变更类型标记：

```markdown
## 变更历史

| 版本 | 日期 | 变更类型 | 变更内容 | 来源 |
|------|------|---------|---------|------|
| v1.0 | 2026-03-01 | 新增 | 初始版本 | 头脑风暴 |
| v1.1 | 2026-03-05 | 修改 | US-003 验收标准更新 | 用户反馈 |
| v2.0 | 2026-03-10 | 新增+删除 | 新增 US-005，删除 US-002 | 需求变更 |
```

### 第五步：定稿确认

向用户展示定稿摘要：

```
✅ 需求文档已定稿！

📄 文件位置：specs/<NNN>-<name>/final-spec.md
📌 版本：v1.0
📊 审查评分：X/100
📝 用户故事：P1 x N, P2 x N, P3 x N
⚠️ 已知限制：N 个

该文档可用于：
  → 开发团队的需求参考
  → AI 编码助手的上下文输入
  → 团队的需求评审会议材料
```

## 常见错误

| 错误 | 正确做法 |
|------|---------|
| 没审查就定稿 | 必须有 review-report.md |
| 定稿后修改 final-spec.md | 修改 requirements.md → 重新审查 → 重新定稿 |
| 不归档旧版本 | 每次版本更新都要归档 |
| 忘记写 Executive Summary | 定稿文档必须有 3-5 句话的摘要 |

## 完成标志

- [ ] 定稿前检查全部通过
- [ ] `final-spec.md` 已生成
- [ ] 旧版本已归档（如适用）
- [ ] 用户已确认定稿内容
- [ ] 下一步指引已提供

# 质量审查

## 概述

对需求规格说明书进行**六维质量检查**，输出结构化的审查报告。这是需求文档的"单元测试"——不测试代码，测试需求本身的质量。

**核心原则：只读审查，不自动修改文档。所有修改由用户决策。**

## 何时使用

- 需求规格说明书已完成（`specifying` 后）
- 澄清阶段已完成（`clarifying` 后）
- 用户要求"检查一下需求文档质量"
- 准备定稿（`finalizing`）之前的最后检查

## 何时不使用

- 文档还在草稿阶段，内容大量缺失 → 先完成 `specifying`
- 有明确的待澄清项 → 先完成 `clarifying`

## 流程

### 第一步：加载全部制品

读取以下文件（如存在）：

1. `specs/<NNN>-<name>/requirements.md` — 主文档（必须存在）
2. `specs/<NNN>-<name>/clarifications.md` — 澄清记录
3. `explorations/<name>.md` — 探索笔记（回溯检查一致性）

### 第二步：六维质量检查

#### 维度 A：完整性

| 检查项 | 说明 |
|--------|------|
| 用户故事覆盖 | 是否有遗漏的关键用户故事？ |
| 角色覆盖 | 所有目标用户角色是否都有对应的用户故事？ |
| 流程覆盖 | 正常流程、异常流程、边界情况是否都考虑？ |
| 非功能需求 | 性能、安全、可用性、兼容性是否都有？ |
| 约束与假设 | 已知约束和假设是否记录？ |

#### 维度 B：一致性

| 检查项 | 说明 |
|--------|------|
| 内部一致 | 不同用户故事之间是否有矛盾？ |
| 术语一致 | 同一概念是否全文使用统一术语？ |
| 优先级一致 | 依赖 P2 功能的 P1 故事？ |
| 探索笔记对齐 | 探索笔记中的决策是否在需求中体现？ |

#### 维度 C：可测试性

| 检查项 | 说明 |
|--------|------|
| 验收标准 | 每个用户故事是否都有 Given/When/Then 场景？ |
| 可量化 | 非功能需求是否有具体数值（非"快速"、"大量"）？ |
| 成功标准 | 整体成功标准是否可客观验证？ |
| 边界值 | 数值类需求是否定义了边界值？ |

#### 维度 D：无歧义性

| 检查项 | 说明 |
|--------|------|
| 模糊词检测 | 是否存在："快速"、"大量"、"合适"、"灵活"、"用户友好"等？ |
| 未解决标记 | 是否还有 `[待澄清]` 标记？ |
| 隐含假设 | 是否有未明说但暗示的假设？ |
| 歧义表述 | "或"、"等"、"如果可能"等模糊连接词？ |

**模糊词检测清单**（发现这些词立即标记）：

```
快速、大量、合适、灵活、用户友好、直观、简单、方便、
高效、可靠、安全、稳定、强大、智能、先进、优秀、
足够、适当、合理、必要时、通常、大部分、某些
```

#### 维度 E：可行性

| 检查项 | 说明 |
|--------|------|
| 技术可行 | 需求是否在现有技术范围内可实现？ |
| 资源合理 | 需求规模是否与预期投入匹配？ |
| 依赖风险 | 外部依赖是否可控？ |

#### 维度 F：优先级合理性

| 检查项 | 说明 |
|--------|------|
| P1 比例 | P1 故事是否控制在 40% 以内？ |
| 依赖顺序 | 高优先级故事是否依赖低优先级的？ |
| MVP 可行 | 只做 P1 是否构成一个可用产品？ |

### 第三步：生成审查报告

使用 @review-report-template.md 模板生成报告。

**严重性定义**：

| 级别 | 含义 | 处理要求 |
|------|------|---------|
| **CRITICAL** | 文档有根本性缺陷（核心用户故事缺失、关键矛盾） | 必须解决后才能定稿 |
| **HIGH** | 重要问题（验收标准缺失、模糊的关键需求） | 强烈建议解决 |
| **MEDIUM** | 改进建议（术语不一致、非功能需求不完整） | 建议解决 |
| **LOW** | 文字优化（表述改进、格式统一） | 可选 |

<HARD-GATE>
审查铁律：

```
审查是只读操作，不自动修改任何文件
```

- 审查报告写入 `review-report.md`，不改动 `requirements.md`
- 用户看完报告后决定是否修改、怎么修改
- 审查者不做"建设性编辑"，只指出问题和建议

```
不因"文档看起来不错"就跳过检查
```

- 每个维度都必须检查，即使预感没有问题
- 至少列出 1 个改进建议，即使是 LOW 级别的
- "完美的文档"不存在，至少提出视角盲区提醒
</HARD-GATE>

### 第四步：呈现结果

向用户展示审查报告的摘要：

```
📋 审查完成！

发现问题统计：
- CRITICAL: N 个（必须解决）
- HIGH: N 个（建议解决）
- MEDIUM: N 个（可选改进）
- LOW: N 个（文字优化）

总体评分：X/100

详细报告已保存到：specs/<NNN>-<name>/review-report.md
```

根据结果建议下一步：
- 有 CRITICAL → "建议修改后重新审查"
- 只有 HIGH/MEDIUM → "建议解决 HIGH 问题后定稿"
- 只有 LOW → "文档质量良好，可以定稿"

## 合理化表

| AI 可能的借口 | 现实 |
|-------------|------|
| "文档看起来很完整，快速过一遍就行" | 每个维度都要认真检查，快速过容易漏 |
| "这些问题太小了不值得提" | LOW 级别的问题也要记录，用户自行决定是否修 |
| "用户会嫌我挑剔" | 审查就是要挑剔，这是审查者的职责 |
| "修改建议我一起帮用户改了吧" | 只读原则不可违反，修改权在用户手中 |

## 常见错误

| 错误 | 正确做法 |
|------|---------|
| 边审查边修改文档 | 只写审查报告，不改源文件 |
| 只看正文不看元信息 | 元信息（版本、日期、状态）也要检查 |
| 报告太笼统 | 每个问题都要指出具体位置和建议 |
| 忘记检查术语表 | 术语表完整性是常被忽略的维度 |

## 完成标志

- [ ] 六维度检查全部完成
- [ ] `review-report.md` 已写入
- [ ] 向用户展示了结果摘要
- [ ] 给出了明确的下一步建议

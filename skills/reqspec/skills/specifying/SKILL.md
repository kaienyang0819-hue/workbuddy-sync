# 需求规格化

## 概述

将清晰的需求意图转化为**结构化的需求规格说明书**。这是 ReqSpec 的核心技能，输出的文档是所有后续步骤的基础。

**核心原则：只关注 WHAT（做什么）和 WHY（为什么），绝不涉及 HOW（怎么做）。**

## 何时使用

- 头脑风暴完成，探索笔记已通过审查
- 用户直接提供了清晰的需求描述（跳过头脑风暴）
- 需要将口头需求或简单描述转化为正式文档

## 何时不使用

- 想法还很模糊 → 先使用 `brainstorming`
- 需求文档已存在，需要修改 → 直接编辑后使用 `reviewing`

## 流程

### 第一步：准备

1. **检查输入**：
   - 如果有 `explorations/<name>.md`，加载它作为上下文
   - 如果没有，从用户的当前描述中提取信息
   
2. **生成编号和目录**：
   - 检查 `specs/` 目录下已有的编号，使用下一个可用编号
   - 创建 `specs/<NNN>-<short-name>/` 目录
   - `<short-name>` 为 2-4 个中文词或英文词（用连字符连接）

### 第二步：提取核心要素

从输入中提取以下要素（如有缺失，向用户确认）：

| 要素 | 说明 | 必需 |
|------|------|------|
| 功能名称 | 简洁的功能标题 | ✅ |
| 背景动机 | 为什么要做这个 | ✅ |
| 目标用户 | 谁会使用 | ✅ |
| 用户故事 | 至少 1 个 P1 级别的用户故事 | ✅ |
| 非功能需求 | 性能、安全、可用性等 | 可选 |
| 约束条件 | 已知的限制 | 可选 |

### 第三步：生成需求规格说明书

使用 @requirements-template.md 模板，填充所有内容。

<HARD-GATE>
遵循以下铁律，违反任何一条都必须立即修正：

```
绝不涉及技术实现细节
```

| 禁止 | 允许 |
|------|------|
| "使用 React 开发前端" | "用户界面应支持现代浏览器" |
| "数据存储在 PostgreSQL" | "系统应可靠地持久化用户数据" |
| "通过 REST API 通信" | "前后端之间应有清晰的接口约定" |
| "使用 JWT 认证" | "用户认证应安全可靠" |

```
每个用户故事必须有可验证的验收标准
```

| 坏的验收标准 | 好的验收标准 |
|-------------|-------------|
| "系统应该很快" | "页面加载时间不超过 2 秒" |
| "用户体验应该好" | "用户完成核心操作不超过 3 步" |
| "系统应该安全" | "连续 5 次错误密码后账户锁定 15 分钟" |

```
NEEDS CLARIFICATION 标记最多 3 个
```

- 对不确定的部分，做合理推断并标注推断依据
- 只有**真正重大影响**的不确定项才标记 `[待澄清]`
- 3 个以上说明输入信息不足，应先回到 `brainstorming`
</HARD-GATE>

### 第四步：用户故事编写规范

每个用户故事必须包含：

```markdown
### US-001 [P1] 故事标题

**作为** <具体角色>，**我希望** <具体行为>，**以便** <业务价值>

**优先级理由**：[为什么是 P1/P2/P3]

**验收场景**：

| 场景 | 前置条件 (Given) | 操作 (When) | 预期结果 (Then) |
|------|-----------------|-------------|----------------|
| 正常流程 | ... | ... | ... |
| 边界情况 | ... | ... | ... |
| 异常处理 | ... | ... | ... |
```

**优先级定义**：
- **P1（必须有）**：没有这个功能，产品无法发布
- **P2（应该有）**：对用户体验重要，但首版可以简化
- **P3（可以有）**：锦上添花，可以推迟到后续版本

### 第五步：自动质量自检

文档生成后，进行以下自检（不需要生成报告，默默修正）：

- [ ] 所有用户故事都有 Given/When/Then 验收场景
- [ ] 功能需求使用"应（MUST）"而非"可以（MAY）"
- [ ] 没有技术实现细节泄露
- [ ] `[待澄清]` 标记不超过 3 个
- [ ] 每个非功能需求都有可量化的指标
- [ ] 术语表中的术语在文档中实际使用

自检最多 **3 轮**。如果 3 轮后仍有问题，写入文档并标注，由后续 `reviewing` 处理。

### 第六步：写入文件

将需求规格说明书写入 `specs/<NNN>-<name>/requirements.md`。

写入后告知用户：
- 文件位置
- 包含多少个用户故事（按优先级统计）
- 标记了多少个待澄清项
- 建议下一步：运行 `clarifying` 消除待澄清项，或直接 `reviewing`

## 常见错误

| 错误 | 正确做法 |
|------|---------|
| 用户故事太技术化 | 用业务语言描述，非开发者也能读懂 |
| 验收标准不可验证 | 必须有具体的数值或明确的是/否判断 |
| 遗漏非功能需求 | 至少考虑：性能、安全、可用性、兼容性 |
| 一个用户故事包含多个功能 | 拆分为独立的用户故事 |
| 优先级全是 P1 | P1 应该控制在总故事数的 40% 以内 |

## 合理化表

| AI 可能的借口 | 现实 |
|-------------|------|
| "用户没提非功能需求，就不写了" | 非功能需求是专业文档的必备部分，基于常识补充 |
| "这个需求太简单不需要验收标准" | 再简单的需求也需要明确何时算"完成" |
| "先写个简单版本，后面再补充" | 每个版本都应该是完整的，可以范围小但不能质量低 |
| "用户已经很清楚了，不需要术语表" | 术语表防止沟通歧义，即使只有 3 个术语也要写 |

## 完成标志

- [ ] `specs/<NNN>-<name>/requirements.md` 已创建
- [ ] 至少 1 个 P1 用户故事
- [ ] 所有用户故事有验收标准
- [ ] 自检通过（3 轮内）
- [ ] 用户已确认文件位置和内容概要

**下一步**：使用 `clarifying` 技能消除 `[待澄清]` 标记，或使用 `reviewing` 技能进行质量审查。
